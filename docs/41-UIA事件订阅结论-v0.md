# UIA 事件订阅结论（R32 / task-54）

- 日期：2026-11-15
- 结论来源：`research/47-uia-events/REPORT.md`（280 行）+ `evidence/`（A/B CSV、JSON、截图）
- 原型代码：`src/Forge.ExternalReader`（`--events` 模式，Release 0 警告 0 错误）
- 性质：研究原型，仍未接入产品主链；ExternalReader 仅作为实验性附加工具（extras）

## 一、一句话结论

**UIA 事件订阅适合做“主通道”，但不能单独承担“不漏读”**——它比轮询快约 2 倍、省约 2.7 倍 CPU，但有秒级尾部停顿；正确形态是
**事件主通道 + 约 2 秒低频轮询对账 + 结构变化定时重扫 + watchdog**。

## 二、A/B 数字（同一 WinForms 夹具，各 60 秒）

| 指标 | 事件订阅 | 轮询 | 说明 |
|---|---:|---:|---|
| 延迟 p50 | 200.2ms | 459.0ms | 改文本→读到 |
| 延迟 p95 | 660.8ms | 956.6ms | |
| 延迟 max | 829.9ms | 1285.1ms | |
| ≤1s 检出率 | 100% | 96% | |
| CPU（单核占比） | 7.41% | 20.26% | 250ms 采样父进程 |

- 另一轮完整 A/B 出现 3 次 >1.5s 空窗（1.87s / 2.36s / 4.87s），p95 升到 1529.7ms、最大 4494.1ms；冒烟轮曾出现约 5.2s 空窗。
  → **尾部停顿根因未定位**（疑 UIA 内部投递/COM 调度），所以不能只靠事件。
- 结构变化事件不可用：夹具 60s 内 25 次增删子控件，只收到 6 个 StructureChanged。新元素发现仍要轮询/重建树。
- 经典 Win32 记事本：18 秒订阅退出码 0、无挂起，但 12 个 NameProperty 几乎都来自状态栏光标位置，正文 Edit 没有可读 Name/Value。
  → 经典 Edit 需改用 TextPattern / Win32 读文本。

## 三、对产品的含义

1. 未知程序兜底（实验性）默认仍保留“轮询”实现；`--events` 作为可选实验开关。
2. 若后续要把事件接入主流程，必须同时保留：
   - 每约 2 秒一次的低频轮询对账（发现事件丢失/空窗）；
   - 结构变化定时重扫（发现新出现/消失的文本元素）；
   - watchdog（事件线程卡住时自动降级回轮询并在日志写明）。
3. 全局焦点事件必须按 pid 过滤；属性事件只订 Name/Value，订阅根用目标窗口 hwnd（`AutomationElement.FromHandle`），不要枚举全桌面（早期探针曾出现约 16 秒空窗）。
4. 经典 Edit 控件需要 TextPattern 或 Win32 读文本，不能只等 Name/Value 事件。

## 四、未验证 / 风险

- 尾部停顿根因未定位；只测了 WinForms 夹具与记事本，未测真实游戏窗口/CEF/Qt/自绘。
- 事件量在复杂窗口（数百元素）下的放大效应未测。
- 本原型只做测量与 CSV，未接 SAPI/NVDA 输出链路的端到端时延。
