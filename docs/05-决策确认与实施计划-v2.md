# GalA11y Forge 产品方案 v2（用户已确认）

日期：2026-11-14　依据：用户 m00298 拍板 + 第一波研究报告（docs/03、docs/04）

## 0. 用户拍板结论（硬约束）

1. 产品形态 = **C 混合**：WinForms 向导 + 确定性流水线。
2. 引擎顺序 = **Unity Mono → Ren'Py → Unity IL2CPP → KiriKiri Z**，其它引擎只做"识别 + 人工待办"。
3. 测试游戏预算 = **上限 ¥300**，先花现有库，需要时再买（候选《钟塔》¥18、《Riddle Joker》¥88）。
4. **实验授权**：允许备份后对指定测试游戏安装/卸载补丁并启动验证；千恋 0.2.0.1 收尾现场除外。
5. **Ghidra**：优先用本机已装版本（本机已有 12.1.4）；允许按需下载；**不随包**。
6. **万能层在 v1 必须包含**，默认标"实验性但可用"。
7. **少用 OCR**：屏幕阅读器本身已有 OCR，我们再做运行时 OCR 价值低、不优雅；只有验证 22MB 级神经 OCR 模型且确实需要时才纳入。
8. 磁盘空间不足：允许清理不必要的文件（由子代理执行，先盘点后删除）。

## 1. 产品一句话（更新）

输入一个 Galgame 安装目录，输出：可安装的无障碍补丁 + 自动分析报告 + 人工待办清单；
已知引擎走精确适配器，未知程序走"通用捕获 + Ghidra 静态分析"的尽力而为路径，绝不以 OCR 为主力。

## 2. 「万能」四层架构（v2 新增，核心变化）

| 层 | 名称 | 能力 | 覆盖对象 | v1 状态 |
|---|---|---|---|---|
| L0 | 引擎适配器 | 精确：剧情/选项/菜单/回放 | Unity Mono、Ren'Py、IL2CPP、KiriKiri Z | 必做 |
| L1 | 通用运行时捕获 | 尽力：抓文字输出 API（UIA/GDI TextOut/DrawText/DirectWrite）、内存字符串、剪贴板/日志 | 未适配的 Win32/自绘/Electron/Qt 程序 | 必做（实验） |
| L2 | 视觉兜底 | 最后手段：截屏 + OCR | 任何能显示文字的程序 | 默认关闭，需验证后才启用 |
| L3 | Ghidra 高级分析 | 未知原生 exe：定位候选文本钩子点、字符串表、交叉引用，导出报告 | 无符号原生程序 | 必做（高级/专家模式） |

分析前门：**保护/加壳检测**（UPX/ASPack/Themida/VMProtect/.NET Reactor/ConfuserEx 检测；只检测不脱商业壳）。

每层都必须输出"覆盖了什么、没覆盖什么、下一步人工怎么做"，不许假装万能。

## 2.5 RE 自动化：产品的真正地基（用户 m00386/m00387 强调）

用户原话："我们这个东西肯定是建立在我们这个已经死命卷 Reverse Engineering 的基础上自动化构建补丁的"。
据此把研发重心明确为 **RE 自动化引擎**，引擎适配器只是"快车道"，不是护城河。

RE 自动化分四块，缺一不可：

1. **静态分析层**（认字）：Mono.Cecil（Unity Mono）、Il2CppDumper/Il2CppInterop（IL2CPP）、Ghidra headless（原生）、PE 头/导入表/字符串（快速分层）。输出统一的证据 JSON。
2. **动态验证层**（对答案）：MinHook/Detours API 监控、Frida 插桩、ETW、Harmony 运行时打点；把静态候选拿到真实游戏里跑，统计命中/漏读/误读。
3. **RE 知识库**（越用越聪明）：从 10 个已发布补丁 + 21 款本机游戏 + 各引擎研究中沉淀"签名"（框架特征、类/方法/字段模式、钩子点模式、置信度规则），新游戏先匹配签名再退回通用分析。
4. **闭环自动化**（产品化）：候选点 → 自动生成钩子代码 → 启动游戏跑指定片段 → 日志统计 → 回流修正评分与签名库。

衡量指标：单款游戏从"给目录"到"可读"的自动完成度、候选点命中率、人工待办条数。v0.1 先在《五天一夜》把闭环跑通，再复制到 Ren'Py / IL2CPP。

## 3. OCR 立场（按用户意见修订）

- 运行时默认**不启用 OCR**；屏幕阅读器（NVDA + 内置 OCR / Windows OCR）已能兜底读屏，我们重复做不优雅。
- OCR 只保留两个位置：
  - A. **分析期取证**：生成分析报告时截屏辅助定位文本区域（不参与运行时朗读，不写入补丁）。
  - B. **用户显式开启的最后手段**（高级选项，默认关）。
- **已实测结论（research/12-ocr-fallback，341 行报告 + 60 份证据）**：
  - Windows 自带 `Windows.Media.Ocr` 零体积、零许可义务；只截对话框区域时识别 25–27ms，截屏+识别+去重+朗读端到端约 0.34 秒；整屏 1920×1080 要 813–1633ms（跟字数走，不可行）。
  - 中文 24px CER 0、18px CER 10%（天/大混字）、12px 可读；必须处理"汉字间插空格"；标点不稳；单字人名行会整行丢失。
  - 本机只有 zh-Hans OCR 语言包，无英/日包；用中文引擎认日文 CER 61%（不可接受），且本机无日语语音——**v1 明确不支持日文 OCR**。
  - 截屏：BitBlt 快但会被遮挡串台；PrintWindow 能取被遮挡窗口（GDI 实测正常），对 D3D/Unity 未实测，需验证是否黑屏；Windows.Graphics.Capture 理论最佳但代码重、需 GPU。
- 22MB 神经模型验证结果：RapidOCR 实际 80–100MB（含 onnxruntime + opencv），PaddleOCR 100MB+，均不满足"22MB"预期；系统 OCR 已够用 → **v1 不引入第三方 OCR 依赖**。Tesseract 5（Apache-2.0，jpn fast 仅 2.36MB）留作 v1 之后日文兜底候选。
- v1 决定：OCR 作为**降级兜底**纳入（钩子失败/未知引擎时），默认关闭，用户在 WinForms 里框选对话框区域 + 前台窗口校验；连续两帧一致才朗读；不承诺独占全屏 D3D 游戏。
- 明确不做：把 OCR 结果硬编码进补丁冒充文本（不优雅且有版权风险）。

## 4. Ghidra 集成策略

- 启动时探测本机 Ghidra（环境变量/常见安装路径/注册表/`ghidraRun`），命中 `12.x` 即用；找不到则提示"按需下载"（校验 SHA256、显示体积），不随安装包分发。
- 高级选项：Ghidra 路径、分析超时、并发数、是否导出报告、报告语言。
- 报告导出：JSON（候选钩子点、证据、置信度、耗时、Ghidra 版本、exe 哈希）+ Markdown（人读版，含"下一步人工验证"）。
- 失败降级：Ghidra 不可用 → 仅做 PE 头/字符串/导入表静态扫描 → 报告标注"未使用 Ghidra"。

## 5. 安全与版权边界（对外写清楚；细则见 docs/10-合规与保护边界-v0.md）

- **分发形态=结构优先**：只发「生成器+运行时注入器+适配脚本」，不发布补丁成品/diff/资源包；用户在本地对自己的正版游戏生成并安装。
- 只处理用户自有的单机游戏；不下载游戏、不传播资源、不绕 DRM/反作弊、不注入在线游戏；检测到在线/反作弊即停。
- 首启风险告知（Steam SSA 禁止修改/篡改、可能封号），默认离线单机模式。
- 生成物只含代码/配置/接口，不含游戏原始台词、图片、音频。
- 脱壳只做检测与合法开源工具（仅 UPX 官方 `-d`，且不覆盖原 exe）；商业壳/商业保护器只提示、不 attach、不提供脱壳或解密。
- 所有第三方组件记录许可证；GPL 与专有二进制不随包，用户自备。
