# 产品架构设计（草案 v0.1，待研究证据回填）

> 状态：Lead 起草，2026-11-14。研究期先定骨架；标 ⚠ 的是待证据/待用户确认的点。

## 1. 一句话架构

一个 **.NET 8 的控制台程序 + 一个 WinForms 向导**，把游戏目录喂进一条**七步流水线**；
每步都产出机器可读的 JSON 证据，任何一步都能单独重跑、单独检查、单独回滚。
引擎差异全部收进"适配器"（每个引擎一个插件），产品主干不认识任何具体游戏。

## 2. 目录与产物协议（工作区）

```
%LOCALAPPDATA%\GalA11yForge\
  games\<slug>\
    profile.json          # 用户可编辑：路径、覆盖项、按键映射、上次结果
    00-detect\detection.json
    01-analyze\analysis.json
    02-decide\plan.json    # 路线 + 置信度 + 人工待办清单
    03-generate\project\   # 生成的补丁工程（源码+工程文件+构建脚本）
    04-build\out\          # 编译产物（DLL/zip）
    05-deploy\deploy.json  # 改了哪些文件、备份到哪、如何卸载
    06-verify\verify.json  # 初检结果：读了什么、漏没漏、错误
    logs\
  cache\                   # 工具下载/解包缓存（可删）
  payload\                 # 产品自带运行载荷：BepInEx、Framework DLL、语音桥、模板
```

原则：**原始游戏目录永不作为工作区**；部署阶段才写入，且写前备份、写后记账。

## 3. 七步流水线与模块接口

| 步 | 接口 | 输入 | 输出 | 失败时 |
|---|---|---|---|---|
| 1 识别 | `IEngineDetector` | 游戏目录 | `DetectionResult`（引擎/运行时/位数/已装 loader/版本线索/证据列表） | 列出"像什么、缺什么证据" |
| 2 分析 | `IEngineAnalyzer` | DetectionResult + 目录 | `AnalysisResult`（文本管线候选、钩子候选、UI 状态、风险、每次探测的原始证据） | 降级为"部分分析"，置信度打折 |
| 3 决策 | `IPlanner` | Detection+Analysis+规则库 | `Plan`（路线 A/B/C/D、内嵌哪些能力、人工待办、预计效果） | 产出"不可自动"报告，不硬上 |
| 4 生成 | `ICodeGenerator` | Plan + 模板 | 补丁工程目录（可编辑） | 生成失败带模板位置与原因 |
| 5 构建 | `IBuilder` | 工程目录 | 产物 + 构建日志 | 区分"环境问题/代码问题/依赖问题" |
| 6 部署 | `IDeployer` | 产物 + 游戏目录 | 部署账本 + 备份 | 自动回滚 |
| 7 验证 | `IVerifier` | 部署账本 + 游戏 | 初检报告（文本流、异常、漏读指标） | 产出"人工复验清单" |

**适配器注册表**：`payload\adapters\<engine>.adapter.json` 声明引擎签名、分析器、模板、能力开关、文档链接。
主干只按注册表调度——新增引擎=加一个适配器，不改主干。

## 4. 生成物形态（补丁工程）

- 语言/框架：C# / .NET（Unity Mono 用 netstandard2.1；IL2CPP 用 net6.0；按 BepInEx 版本路由）。
- 依赖：产品自带 `payload\framework\` 里的 `A11y.Framework.dll`（L1 平台层）+ `A11y.Contract.dll`（L2 契约），
  版本固定、随产品发布，生成物无需联网/无需 clone 用户仓库。
- 每个生成物包含：
  - `Plugin.cs`（入口、生命周期、日志）
  - `Hooks\<engine>.cs`（由分析结果生成的钩子代码；无候选时生成"待人工"占位并写 TODO）
  - `game.profile.json`（该游戏的指纹/钩子配置/按键）
  - `build.ps1` / `build.cmd`（调用 dotnet，检查产物哈希）
  - `README-用户版.md`（中文说人话：怎么装、怎么用、怎么卸、怎么报错）
  - `LICENSE` + 第三方声明
- 硬规则：**不含游戏资源/台词/图片/音频**；钩子只读游戏数据，不改游戏逻辑。

## 5. 决策规则（路线分级）

- A 自动通过：引擎有成熟适配器 + 关键钩子候选高置信 + 构建通过 + 初检通过。
- B 自动+人工确认：适配器可用但某些候选低置信 / 需要用户选一项（如"朗读哪一层文本"）。
- C 半自动：只能生成骨架 + 人工待办清单（逐作 RE 的游戏）。
- D 不支持：明确告知原因与替代方案（例如先用通用保底模式）。

置信度来源：签名强度、候选数量与分布、同名/同模式复用、历史作品匹配、构建/初检结果。

## 6. 对读屏友好的 GUI（WinForms）

- 纯键盘可完成：Tab 顺序固定、Enter 默认动作、Esc 返回、快捷键标注在控件文本里。
- 每个控件有 `AccessibleName/Description`；进度用文本播报（"第 3 步，共 7 步：正在分析"）。
- 主界面只有三块：**选游戏 → 看方案 → 点开始**；高级参数收进"高级"页。
- 结果页把"机器做了什么/还差什么/怎么验证"逐条列出，可复制为文本。
- 出错页给"下一步"而不是堆栈；日志按钮一键打开目录。

## 7. ⚠ 待研究证据回填的关键决策

1. 分析器技术路线：Unity Mono 用 Mono.Cecil 静态扫描够不够？IL2CPP 是否必须 Il2CppDumper/Cpp2IL？——R4/R5。
2. 语音桥形态：内嵌 Tolk + NVDA controller + SAPI 降级，还是只发消息给外部读屏？——R6。
3. 非 Unity 适配顺序与形态：Ren'Py overlay 生成 / KiriKiri 注入 / RPG Maker JS 插件。——R4/R1。
4. 依赖分发方式与许可证：BepInEx、Tolk、Framework 的再分发边界。——R5。
5. GUI 技术：WinForms vs WPF（读屏兼容性与开发成本）。——R6/R8。
6. 首验游戏选哪个：小体积、Unity、未装补丁、文本结构清晰。——R3。

## 8. 测试策略（先测试后代码）

- 单元：检测器（指纹表驱动）、分析器（合成程序集/合成脚本）、规划器（规则表）、生成器（golden 文件对比）、部署器（沙箱目录+回滚断言）。
- 集成：用"假游戏夹具"（合成 Unity Mono 目录 + 小 DLL + 假文本源）跑完整七步。
- 真实验证：至少 1 个未装补丁的 Unity 游戏全自动生成 + 1 个已装补丁游戏复验（不破坏）。
- 回归：每个已支持引擎至少 1 个案例进 `tests/golden/`。
- 每个测试必须能回答："哪一步错了、证据在哪"。

## 9. 失败与回滚

- 部署前：记录游戏目录全部改动文件的 SHA256 + 原文件备份到 `05-deploy\backup\`。
- 卸载：按账本反向恢复；额外提供"Steam 校验文件完整性"指引。
- 构建/部署失败：自动回滚到部署前状态；验证失败：保留部署但给出"卸载"与"继续人工试"两条路。
- 绝不动游戏存档目录（除非用户显式选择备份存档）。

## 10. 对外说法（避免夸大）

- 产品定位："半自动到全自动，按引擎分级"；不承诺"一键支持所有 Galgame"。
- 每个游戏结果页都写清：本次自动到哪一步、置信度、未验证项。
- 版本号从 0.1.x 起，功能稳了再加。
