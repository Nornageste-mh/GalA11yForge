# GalA11y Forge（无障碍补丁工坊）项目总览与方案 v0

- 文档版本：v0.0.1（草案，2026-11-14）
- 状态：**阶段 0 研究期**——产品代码尚未开始；研究证据回来后进行 A/B/C 形态确认
- 目标：见会话目标 `goal-460a1a99`（256 轮长期目标）

---

## 一、我们要做什么（一句话）

做一个 Windows 程序：你选一个游戏文件夹，它自动判断这个游戏"能不能读屏玩、该怎么读"，
然后把补丁工程生成出来、编译好、装进去、做一次初检；不能全自动的地方，用中文告诉你
"卡在哪一步、需要人做什么"。

它要解决的不是"再写一个补丁"，而是"把前面 10 多个补丁里反复做的人工流程，变成一台机器"。

## 二、为什么有底气做（前期资产）

1. 已有 **Framework**（可复用平台层 L1 + 契约层 L2）：语音、按键边沿、热键、NVDA/ZDSR/SAPI 通道、
   UI 导航、重复朗读控制都已打磨过，并且已从三个已发布补丁里反向固化。
2. 已有 **10 个以上已发布补丁**，覆盖 Unity Mono、Unity IL2CPP、Ren'Py、KiriKiri Z、NVDA 双进程。
3. 已有 **半自动骨架生成器** `Framework/tools/new_game.py`：能根据参数生成 Unity 补丁工程骨架，
   但遇到 Ren'Py / KiriKiri 会主动拒绝，且"分析、决策、验证"仍靠人。
4. 本机 **Steam 有 20 个游戏**，覆盖 Unity Mono 6 / Unity IL2CPP 5 / Ren'Py 3 / KiriKiri Z 1 / 其他 4，
   其中 5 个未装补丁，可直接当"全自动生成"的首验对象。
5. 社区里有成熟参照：boz700908 的模板化打法、prism 抽象层、Aokana 大而全补丁、Textractor 等工具生态。

## 三、产品形态：三个选择（当前推荐 C）

### A. 纯命令行生成器（像"编译器"）

输入：游戏目录 + 少量参数；输出：补丁工程源码 + 编译产物 + 安装说明。
- 优点：实现最直接；复用 new_game.py 最快；无运行时风险。
- 缺点：普通玩家用不了（要会命令行）；每个游戏的关键钩子仍可能要人调；
  "自动"只到"生成骨架"这一层。
- 适合：先做骨架、后续再包 GUI。

### B. 通用运行时插件（一键安装，不生成代码）

做一个"万能读屏插件"：装进游戏，靠运行时内存/文本捕获 + 通用语音桥，不针对单个游戏生成补丁。
- 优点：体验最接近"一键"；不用为每个游戏编译；更新游戏后不易失效。
- 缺点：通用文本捕获在 Unity IL2CPP 上很难可靠（乱码、拿错串、漏句、把 UI 文本当台词）；
  Galgame 的"该读哪一句、选项怎么报"高度依赖游戏逻辑，通用方案通常效果差；
  你已有 10 个补丁的经验恰恰证明"每个游戏都要定制"。
- 适合：作为"保底模式"（生成器失败时也能勉强读）。

### C. 混合：通用保底 + 按游戏生成（推荐）

- 内置 B 的通用读屏能力作为**保底**：装上去至少能读一部分，不保证质量。
- 生成器（A 的增强版）负责**精调**：自动识别引擎、自动分析候选文本管线、生成专用补丁工程、
  编译、部署、初检；人工只处理"机器拿不准"的少数点。
- 优点：先保证"能用"，再追求"好用"；风险分散；和已有资产/经验对齐。
- 缺点：工作量最大，需要两套能力；但可以分阶段做（先 A 后 B，最后合成 C）。
- **建议：按 C 立项，先交付 A 的能力，B 作为第二期。**

## 四、流水线七步（机器模块划分）

| 步骤 | 做什么 | 机器能做的 | 可能留给人 |
|---|---|---|---|
| 1 识别 | 判断引擎/运行时/位数/已装补丁 | 签名扫描 + PE 头 + 目录特征 | 极少 |
| 2 分析 | 找"文本从哪来、界面有哪些状态" | 静态扫描程序集/脚本/资源索引 | IL2CPP 深层逻辑、加密脚本 |
| 3 决策 | 选适配路线与钩子方案，给置信度 | 规则库 + 打分 + 生成"体检报告" | 低置信度时人定 |
| 4 生成 | 产出补丁工程（代码+配置+构建脚本） | 模板 + 参数化 + 代码注入点 | 特殊 UI 的手工微调 |
| 5 构建 | 编译、打包 | 调用 dotnet/msbuild，检查产物 | 环境坏了 |
| 6 部署 | 安装到游戏目录（含备份/回滚） | 复制、备份、写配置、生成卸载 | 杀软拦截确认 |
| 7 验证 | 启动游戏做初检，产出报告 | 读日志、自检文本流、比对预期 | 人工试玩确认 |

关键设计：每一步都可单独跑、可跳过、可重入；产物带"哪一步做的、证据是什么、置信度多少"。

## 五、分阶段路线

- **阶段 0 研究（进行中）**：8 名研究员并行，产出一手证据（生态/引擎/工具/无障碍栈/社区/竞品）。
- **阶段 1 方案确认**：汇总研究 → 给用户 A/B/C 确认 + 架构规格 + 测试策略 + 成本表。
- **阶段 2 核心流水线**：识别 → 分析 → 决策 → 生成（先 Unity Mono + IL2CPP），单元测试全绿。
- **阶段 3 适配器**：Ren'Py 覆盖层、KiriKiri 注入、RPG Maker 插件，按可行性排序。
- **阶段 4 体验层**：可访问 GUI（纯键盘+读屏可用）+ CLI（JSON 输出，便于自动化）。
- **阶段 5 真实验证**：在 Steam 现有游戏上跑端到端（至少 1 个未装补丁游戏），含卸载回滚，
  产出一份"人工复验清单"给你照着点。
- **阶段 6 交付**：文档、打包、成本分析、被打回预案、发布草案。

## 六、质量与安全底线

1. **不扩大可达范围**：补丁只做"原游戏本来就能做的操作"的读屏化，不代打、不解锁隐藏内容。
2. **IP 红线**：生成物不包含游戏资源/台词；只含代码与接口。
3. **测试先行**：单元测试全绿 + 真实游戏实测；未实测的功能在文档里明确标注。
4. **可插拔/可快速修正**（为你"被打回"准备）：
   - 引擎适配器、语音后端、钩子策略、UI 都是独立模块，坏一个不拖垮全链；
   - 每个游戏生成一个可编辑的 `profile`（游戏指纹、钩子配置、按键映射），打回后改配置即可重生成；
   - 生成物允许"人工覆盖文件"：重生成时保留用户手改部分。
5. **可回滚**：部署前备份，一键卸载；不污染 Steam 文件完整性（记录改动清单）。
