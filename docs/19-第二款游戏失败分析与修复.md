# 19. 第二款游戏真机失败分析与修复（2026-11-14）

> 目的：记录 NEEDY GIRL OVERDOSE（Steam appid 1451940，Unity Mono 2022.3.22）真机 E2E 的完整失败链，
> 以及由此触发的修复与待办。对应任务卡 task-27（已完成，结果 FAIL），报告
> `research/22-second-game/REPORT.md`（309 行）。

## 1. 结论（先看这里）

1. **第二款游戏没能「生成即读」**：不是单点 bug，而是三层叠加——选点（钩子没有文本参数）、构建（Unity API 被裁剪）、加载（BepInEx 5 预加载器崩溃）。
2. **好消息：回滚是干净的**。两次部署后回滚都删除 23 个文件、清理 3 个目录，1058 个基线文件 SHA-256 全一致；原版可正常启动。
3. **`verify` 曾把「插件根本没加载」报成通过**——这是最危险的产品缺陷。现已修：日志缺失/为空一律判 **失败**，并额外识别 `preloader_*.log` 崩溃日志；`pass_with_skips` 在文案上不再说「通过」。
4. 现在产品对 Unity Mono 的适用边界更清楚了：**文本写法可静态识别 + Unity API 完整 + BepInEx 5 能加载**，三条同时满足才有机会自动成功。缺一条就必须降级为人工待办，不能假装成功。
5. 由此新增两项工作：R20 加载器/构建兼容性探针（task-33，子代理执行中）、安装前基线自动生成（task-34，子代理执行中）。

## 2. 三层失败（[实测]）

### 2.1 选点层：6 个钩子全都没有字符串参数

- `forge analyze` 对 NEEDY 给出 50 个候选，plan 选了 6 个，全部是 `*Dialog::OnLanguageChanged()` 类方法，签名里没有 `System.String`。
- 生成器按设计把 6 个 Hook 都标为 `skeleton_unwired`，Postfix 只做调用计数；即使后面全部成功也不会出现 `[Speech]`。
- 根因：该作真正的台词文本不在这些“换语言刷新”方法里，静态打分只看到 TMP 写入点密度，选错了面。

**已修**：`forge plan/generate/build/install/report` 在计划不含任何字符串参数补丁点时打印明确警告：
> [警告] 本次计划的补丁点都不含字符串参数：生成物只能记录调用次数，不会朗读。请按报告的人工待办人工指定文本来源……

**待办**：选点规则加强（跨类追踪文本字段写入、把“刷新/换语言”方法与“显示文本”方法区分开）；这条属于 P1，后续波次做。

### 2.2 构建层：`Input.anyKeyDown` 不存在

- 原生 `forge build --bepinex` 报 `CS0117: "Input" 未包含 "anyKeyDown"`（`Platform/KeyEdge.cs(282,38)`）。
- 该作的 `UnityEngine.InputLegacyModule.dll` 只有 19,456 B，只剩 `Input.anyKey`；同机另外 8 个 Mono Unity 游戏都有 `anyKeyDown`。
- 说明生成工程假定 Unity API 一定齐全，这个假设不成立。

**待办**：R20 探针（task-33）做“构建前 API 存在性检查”，缺失时降级生成/给出人工待办，而不是硬编译失败。

### 2.3 加载层：BepInEx 5 预加载器崩溃

- 为继续验证，子代理在生成物里加了临时 Input shim（**非产品修复**，报告已标注），构建/安装成功。
- 启动游戏时 BepInEx 5.4.23.5 预加载器崩溃：
  `MissingMethodException: Method not found: void System.Reflection.Module.GetPEKind(...)`。
- 该作 `mscorlib.dll` 只有 2.73 MB（同机 8 个 Mono 游戏均 4.63 MB 且含该符号）→ Unity 裁剪导致 BepInEx 5 不兼容。
- 结果：无 `LogOutput.log`，BepInEx 目录无配置，插件 0 加载，游戏本体照常开场——**静默失败**。

**待办**：R20（task-33）实测 BepInEx 6 / MelonLoader 在 NEEDY 副本上能否加载最小插件；产物是“加载器兼容判定 + 明确人工待办”，不是硬修。

## 3. verify 假通过：已修（本轮 Lead 直接改）

- 旧行为：`BepInEx/LogOutput.log` 不存在 → b-05/b-06 记 `Skip` → overall=`pass_with_skips`，文案“初检通过”。
- 新行为（`src/Forge.Verify/Internal/BepInExChecks.cs`）：
  - 日志不存在/为空 → b-05（P1）与 b-06（P0）**Fail**，detail 明确写“启动一次游戏后重跑；这不等于通过”；
  - 同时扫描游戏根目录 `preloader_*.log`，有则写进 detail（“发现预加载器日志：…（BepInEx 很可能没有加载成功）”），日志存在但缺加载行时也会附带该提示；
  - CLI（`src/Forge.Cli/PipelineCommands.cs`）文案纪律：`pass` 才说“初检通过”；`pass_with_skips` 说“初检完成但有 N 项未验证，不等于通过”。
- 测试：`tests/Forge.Verify.Tests` 由 59 → **60 通过**（改 2 个旧语义用例 + 新增 preloader 崩溃用例）；全解决方案见 §5。

## 4. 回滚与残留（[实测]）

- 部署：`forge install --force` → 23 个文件操作；回滚：`forge verify --rollback --force` → 还原 0 / 删除 23 / 清理 3 目录，哈希不一致 0。
- 最终 1059 个文件 = 1058 个安装前基线文件（SHA-256 全同）+ 游戏首次运行自建的 `Windose_Data/settings.es3`（1,226 B，JSON 头含 RESOLUTION/UNLOCKEDZIP）。该文件**不属于补丁**，删掉会重置游戏设置，建议保留。
- 首次启动产生的 `preloader_20261114_200051_097.log` 已在复制到 evidence 后手工删除；无 BepInEx / winhttp / doorstop 残留；原版 `Windose.exe` 启动正常。

## 6. 对“相对万能”的诚实说明

NEEDY 这类游戏说明：**“万能”不能靠同一条自动流水线硬吃所有游戏**。当前可行的产品承诺是：
- 能识别引擎（22/22 实测）；
- 能静态分析出候选，并**在候选不够时明确降级**（人工待办 + 警告）；
- 能生成/构建/安装/回滚/自检一条龙，并在每个环节**只报证据支持的成功**；
- 遇到 Unity 裁剪、加载器不兼容、文本写法不可静态识别时，给出可执行的人工待办，而不是静默失败。

这与用户“不要只是看了我们这么几个游戏就只能做这些，它应该相对万能”的目标方向一致：万能来自**兼容性探针 + 降级策略 + 可插拔适配器**，不是来自假装所有游戏都能自动成功。
