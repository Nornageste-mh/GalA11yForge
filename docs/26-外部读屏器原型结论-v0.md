## 一、结论先行（人话）

**部分可行，只承诺“标准控件/可访问网页外壳”。**

1. **自控 WinForms 演示窗**：UIA 能读到全部文本；43 秒里正确捕获 10 句循环台词，去重后朗读 22 句；F8 暂停/继续、F9 重读、F10 退出四个热键全部生效；无崩溃、无泄漏。→ **这类窗口 v1 可以承诺。**
2. **LoveNest（NW.js/Chromium 71 自绘）**：整窗 UIA 只有 23 个节点、12 条文本，全是窗口外壳；正文一条都没有；MSAA 3 个空节点；`--force-renderer-accessibility` 无变化。→ **这类当前读不到，且不是“Chromium 一律读不到”（同机新版 Chrome 的 DOM 正文可读，说明是应用/引擎版本没暴露无障碍树）。**
3. **OCR 救不了自绘游戏**：干净 UI 字体中文长句 CER 2.2%（整体 10.7%）；LoveNest 美术字体对话 CER 41.8%、加载页 70.6%；单帧 0.18–0.7s。→ 读出来的句子玩家听不懂，**默认关闭、只作实验功能**。

## 二、对产品的直接影响

- 原“万能层 v1”承诺需要改成两句话：
  - 可以说：“不需要给游戏打补丁，只要界面是标准控件或可访问的网页外壳，就能读。”
  - 不能说：“什么游戏都能读。”
- 外部读屏器（`src/Forge.ExternalReader`）**不进主链**，作为**实验性附加工具**：
  - 不随 0.2.2 主包发布（已发布，不追改）；
  - 0.2.3 起可作为独立 exe / extras 放进发布包说明；
  - 默认不随主 CLI 安装，避免用户误以为“万能”。
- OCR 只在用户显式开启时运行，文案写“实验性：请框选对话区，字体清晰才有效；本机仅中文识别引擎”。

## 四、已实测的环境/机制事实（便于后续复用）

- UIA 单次跨进程调用约 20–27ms；原型靠“时间预算 + 每节点通道缓存（15s）+ ControlType 定制读取顺序”把轮询压到可接受。
- 去重三层：①同 NodeId 文本稳定 `settleMs`；②与上一句相同且 <3s 丢弃；③同 NodeId 同文本不再念。
- 朗读队列：独立 STA 线程 + 有界队列（max 4），SAPI 走 ISpVoice vtable（异步），NVDA 走 `nvdaControllerClient64.dll`，NVDA→SAPI→Null 三级降级；**后端必须在线程内 Dispose**（跨套间 Release 会 0xC0000005，原型第一版就崩过）。
- 热键：RegisterHotKey 独立线程消息泵（F8/F9/F10）。
- 日志只写 `%TEMP%\forgereader\` 或工作区，**不写游戏目录**。
- 依赖：FlaUI.UIA3 4.0.0（MIT）、FlaUI.Core（MIT）、Interop.UIAutomationClient（MIT）、Microsoft.Windows.SDK.NET.Ref（MIT）；`nvdaControllerClient64.dll` LGPL-2.1 不随包，只在用户机器探测。
- 未测/待确认：Ren'Py（DDLC 未启动，避免写游戏目录，故用 KiriKiri/Unity 只读对照）、NVDA 真实出声（只到调用层）、x86 游戏、DPI≠100%、多显示器、独占全屏。
