# AI 可用性测试方案（替代真人 Round A）

> 状态：已确定（依据用户 2026-11-15 18:01 邮件：不邀请真人，AI 相关测试不受限制）。
> 取代 `docs/63-可用性测试RoundA方案-v0.md`（该文只作历史记录，不再执行）。

## 1. 为什么改

真人 Round A 需要招募视障玩家、约时间、付费补偿，用户明确不做。改成 AI 测试后：

- 成本为零，可反复跑；
- 关注点从“真人第一次用会不会卡”调整为“流程在自动化/读屏/语音链路上是否真的通”；
- 不能替代真人主观体验——报告里必须写清“AI 测试不等于真人可用性结论”。

## 2. 三层 AI 测试

### L1 自动化 E2E（已有基础）

- 用脚本驱动 CLI/GUI：detect → analyze → plan → generate → build → install → verify → rollback；
- 每个受支持引擎（Unity Mono / IL2CPP / Ren'Py）各挑一款样本；
- 判定：退出码、JSON `ok`、关键日志行、回滚后哈希一致。

### L2 读屏与语音链路自动校验

- GUI：用 UIA 树 + `AutomationId`/Name 断言控件可读、Tab 顺序、快捷键（现有 `uia-tree.txt` 升级为断言）；
- 朗读：WASAPI loopback 抓包（已有工具）比对按键与音频段一一对应；NVDA 用“朗读查看器/日志”作为第二证据；
- 反向用例：Tolk 缺失、NVDA 未开、SAPI 音量 0 时的降级行为。
- **已落地（0.2.20）**：`forge verify --speech-log <日志>` 自动统计有效/去重/占位朗读行，并给出 `s-01..s-03` 三项检查；真机演示见 `research/62-speech-log-verify/`。

### L3 AI 操作模拟（探索性）

- 用 Agent 自己当“玩家”：读日志、点按钮（client 坐标）、推进剧情、走选项；
- 允许失败并记录：卡在哪里、日志是否给出可行动提示；
- 不写“AI 觉得好用”，只写“AI 完成/未完成、用了多少步、卡点是什么”。

## 5. 诚实边界（写进后续发布说明）

- AI 测试能证明“链路通、日志对、音频有”，不能证明“盲人用户真的觉得好用”。
- 若后续用户能安排真人，再做一轮小规模真人验证；在此之前不对外宣称“经过真人可用性测试”。
